0一页速览

先给结论：这四者不是四选一，而是一条从探索到契约、再到验证的抽象阶梯。同一个项目里它们同时存在，只是各自负责不同的问题。

L4
结果驱动
业务结果是否达成——产物是"流失率下降 15%"这类指标。这是前沿，尚未定型。
L3
SDD
规格是否完整捕获了意图——产物是 spec / constitution / tasks，人和 AI 的共同真相来源。
L2
BDD
用户能不能完成这个流程——产物是 Given-When-Then 场景，可执行、可被非技术角色读懂。
L1
TDD
这个函数/单元是否返回了正确结果——产物是测试，最快、最确定的一层。

抽象阶梯：每一层都包含下一层。人往上走的距离，就是人提供独特价值的距离。Vibe Coding 不在这条阶梯上——它是用来发现该往哪一级建的探路工具。

四句话分工

模式回答的问题一句话定位
Vibe Coding这东西到底该长什么样？让你"快速做出来"——用可丢弃的代码换取认知

五条关键洞察

  1. 当代码生成趋近零成本，规格成为最贵的资产。GitHub 的说法很直白："维护软件意味着演进规范；开发的通用语言上升到更高层次，代码只是最后一英里的方法。"
  2. 测试的角色变了。传统开发里测试是"保障代码质量的工具"；在 AI 编码里，测试是"约束 AI 行为的执行器"。它还顺带解决一个具体问题——AI 幻觉出一个不存在的库或方法时，测试会立刻编译失败，而不是三天后才发现。
  3. BDD 因为 AI 而复兴。它曾被认为是为了仪式而仪式（SpecFlow 被 Tricentis 放弃、Cucumber 移交社区、多数团队跳过 Discovery 直接写 Gherkin）。但 agent 没有"人会意"的能力：人能从模糊的 ticket 和 Slack 对话里推断出 PM 的意思，agent 不能。它需要无歧义的指令。"Agents don't need opinions. They need instructions."
  4. SDD 不是新概念。它是 Design by Contract（Meyer, 1988）、TDD（Beck, 2002）、BDD（North, 2006）与模型驱动工程在现代 LLM 上汇合的结果。理解这一点能避免一次典型误判——把它当成又一次方法论炒作。
  5. 没有护栏的 AI 速度是债务加速器，不是产能放大器。Google 2025 DORA 报告的结论是：AI 同时提升交付吞吐和不稳定性，因为它放大的是团队已有的实践。强队更快，没有评审/测试/明确归属的团队只是更快地生产需要重做的工作。
三条判断法则

① 如果这段代码你下周还会碰，就值得用 SDD。
② 快速原型、一次性脚本、技术可行性探索、个人小工具——放手用 Vibe Coding，它的"快"无可替代。
③ 生产环境核心业务代码、多人协作（>2 人）、持续迭代超过 3 个月、对稳定性和可追溯性有要求的场景——上 SDD。

1四个模式：来源与核心机制

Vibe CodingKarpathy, 2025

放弃阅读代码，靠对话和运行结果迭代。

  • 核心动作：描述意图 → 生成 → 看结果 → 自然语言反馈
  • 定义要害：不接受代码审查，"Accept All"，不读 diff
  • 作者自划边界：throwaway weekend projects
  • 适合：探路、原型、一次性脚本、学习
TDDBeck, 2002

先写失败的测试，再写刚够通过的生产代码。

  • 核心动作：Red → Green → Refactor
  • 三条规则：不为通过测试就不写生产代码；只写刚好失败的测试；只写刚好通过的生产代码
  • 层级：单元 / 方法级（内环）
  • AI 时代变成：测试即精确提示词 + 退出条件
BDDNorth, 2003/2006

用业务语言的具体例子描述系统行为，并让它们可执行。

  • 三个实践：Discovery → Formulation → Automation（多数团队只做了第三个）
  • 协作机制：Three Amigos / Example Mapping
  • 层级：功能 / 场景级（外环）
  • 副产品：活文档 + 统一语言
SDDMeyer→Spec Kit, 2025

规格是唯一事实来源，代码是派生产物。

  • 核心动作：Specify → Plan → Tasks → Implement → Verify
  • 三层成熟度：Spec-first / Spec-anchored / Spec-as-source
  • 层级：战略层，管"做什么 + 不做什么"
  • 关键机制：constitution（非可协商原则）作长期护栏

1.1 Vibe Coding：被误解最深的那个

2025 年 2 月 6 日，Andrej Karpathy 提出这个词："There's a new kind of coding I call 'vibe coding', where you fully give in to the vibes, embrace exponentials, and forget that the code even exists." 他描述的具体行为包括——用语音跟 Composer 说话、提"把侧边栏内边距减半"这种懒得自己找的蠢需求、永远 Accept All、不再读 diff、报错就原样粘贴回去。

这个定义比大多数引用者以为的窄得多。Simon Willison 在 2025 年 3 月专门写文章收紧它："If an LLM wrote every line of your code, but you've reviewed, tested, and understood it all, that's not vibe coding in my book—that's using an LLM as a typing assistant." 他的判别线只有一条：你有没有读你提交的代码。"Vibe coding your way to a production codebase is clearly risky. 我们作为工程师的大部分工作是在演进既有系统，而这些代码的质量和可理解性至关重要。"

词的生命周期说明了它的影响力：Collins 词典 2025 年度词汇；Merriam-Webster 于 2025 年 3 月以"slang & trending"收录。随后两边都获得了专有名称——Willison 在 2025 年 10 月提出 vibe engineering，描述"资深工程师用 LLM 加速、同时保持对产出骄傲且自信地负责"；Karpathy 在 2026 年 4 月提出 agentic engineering，指"针对详细规格指挥编码 agent 的纪律，而不是指望一句 prompt 恰好落在有用处"。

代价的数据面

代码结构在退化。GitClear 2026 年 1 月对 6.23 亿次代码变更的研究：重复代码块 +81%，提交内复制粘贴 +41%，而重构（搬移和合并既有代码）-70%——重构从 2022 年占改动行的 21% 掉到 2026 年的 3.8%；掩盖错误而非处理错误的构造 +47%。每一条都是未来的账单：重复逻辑意味着你在一处修了 bug、在另外四处留着；重构缺席意味着代码库每周更难改；掩盖错误意味着故障在客户发现前一直不可见。

信任度极低。Stack Overflow 2025 年近 5 万人的调查：84% 使用或计划使用 AI 工具，但只有 3.1% 高度信任其产出准确性，45.7% 明确不信任。最困扰的问题是"几乎正确、但不完全"（66%），其次是调试 AI 生成代码耗时（45.2%）。"几乎正确"是最贵的一类，因为完全跑不起来反而便宜。

生产力感知是失真的。METR 2025 年 7 月的随机对照试验：16 名资深开源开发者，允许使用 AI 后完成任务反而慢了 19%，而他们事后自评"快了 20%"。

安全没有跟着变好。Veracode 2025 年 10 月：三年间 LLM 生成功能性代码的能力大幅提升，但生成代码的安全性基本没有改善，大模型也不比小模型更擅长生成安全代码。Lovable 2025 年 5 月的案例中，1645 个生成的 Web 应用里有 170 个存在任何人可访问个人信息的问题。

三个月墙

纯 Vibe 项目有相当可预测的衰变曲线：兴奋期（1–3 月）高产出，"AI 一天搞定一个功能"；平台期（4–9 月）停滞，"为什么新功能总是破坏旧功能"；衰退期（10–15 月）崩溃，"这坨代码没人能维护，不如重写"。根本原因是零上下文编程：当代码膨胀到几万行，AI 的上下文窗口装不下全貌，开始基于局部信息做决策，而这些决策与其他模块冲突。

诊断：Vibe Coding 的失败不是因为 AI 不够强，而是因为意图没有被结构化。

1.2 TDD：在 AI 时代从"好实践"变成"必需品"

传统 TDD 的价值叙事是"更好的设计"和"更少的回归"。AI 时代的价值叙事完全不同：它提供了确定性的退出条件。Simon Willison 的表述被反复引用："Tests give us reliable exit criteria. We are not relying on AI agent's whims, but we force it to iterate until the previously failed tests pass."

原因在于 AI 编码引入了一个传统开发里不存在的问题：非确定性。同一个 prompt 可以跑出结构完全不同的实现。你的质量保障不能再依赖"这次生成的代码看起来还行"，必须有外部判据。

升级后的循环：Test → Drive → Develop

Red人（或人审查 AI 草稿）写失败测试，覆盖正常路径 + 边界 + 错误条件
GreenAI 生成实现，唯一目标就是让这条测试通过
RefactorAI 清理逻辑，约束是"保持所有测试绿色"
Validate人审查产出，决定接受或再来一轮

对应地，四个"为什么测试让 AI 编码更好"的机制：测试即提示词（精确规格降低歧义和幻觉）；建立信心（绿色是证据，不只是"看起来对"）；抑制范围蔓延（紧的测试边界阻止 AI 过度设计）；即时捕获回归（重构变安全）。

一个有说服力的真实案例

某团队在税务计算模块上遇到：AI 建议用"单价 × 数量"这种简单乘法，看起来完全正确。但测试专门检查了法定舍入要求——必须在小计层级舍入，而不是在行项目层级。于是 AI 的初版代码立刻失败。没有 TDD 的话，这个偏差会直接进生产，带来合规风险和营收对账错误。

另一个：B2B 合同规则"买 10 件以上、仅对达标行项目打 9 折"。AI 生成的实现是零售场景的常见写法——对整张发票总额统一打折。因为是行项目级的验收测试，这个"看起来完美"的代码同样立刻失败。

AI 时代新增的纪律

  • 先提交测试，再提交实现。这既强制了纪律，也让 PR 可评审。
  • 写测试和写实现用不同 session / 不同 agent。不要让它们共享上下文——共享就意味着 AI 会为自己的实现写自洽的测试。
  • 测试命名描述行为。it('should reject payments over the daily limit')，不是 it('test payment')。
  • 一个测试一个行为。范围收紧，AI 的发挥空间也就收紧。
  • 看见红。在任何生产代码改动之前，必须亲眼看到测试是红的。这是防止"测试其实是装饰"的唯一手段。

1.3 BDD：一条从"形式主义"到"必需品"的回归曲线

Dan North 在 2003 年提出 BDD，起因不是测试技术问题，而是语言问题：开发者抗拒 TDD，不是因为技术实践难，而是因为"不知道该测什么、测试该叫什么名字、从哪开始"。BDD 把焦点从"测试"移到"描述行为"。2004 年 Chris Matts 提出 Given-When-Then 画布，2006 年 North 发表《Introducing BDD》，2008 年 Aslak Hellesøy 的 Cucumber 让 Given-When-Then 记法普及开来。

BDD 的三个实践里，Discovery 才是价值来源，Gherkin 只是它的记录格式。这一点是 BDD 历史上最大的执行偏差：大多数团队跳过了 Three Amigos 会议，由开发者先写代码、事后补 Gherkin——规格于是变成"已建成之物的文档"，而不是"应当建成之物的规格"。这也是它后来被嫌弃的原因。

AI 把这三件事重新排序了：

  • 技术门槛消失了。产品经理可以直接用自然语言写场景，AI 自动翻译成可执行测试。Three Amigos 协作终于不必经过技术守门人。
  • 语义定位取代了脆弱选择器。AI 驱动的测试运行器按上下文而不是 CSS 选择器定位 UI 元素。
  • 活文档名副其实。场景既是文档又是测试，因此永远不会过期。

更本质的联系来自 Thoughtworks 的 Birgitta Böckeler：spec-by-example 本质上是"few-shot prompt 技术"应用于软件需求。这个类比解释了为什么 BDD 在 AI 时代突然变得高效——你在做的事情，正好是给模型提供带具体输入输出的示例。arXiv 的研究也给了量化支撑：人工精炼的规格可以把 LLM 生成代码的错误减少最多 50%。

为什么 BDD 是必要的：打破自我确认闭环

Tests Pass ≠ It Works

这个场景极其常见：AI 生成代码 → 生成测试 → 测试通过 → 你发布 → 用户发现了一个测试本该捕获的 bug。原因是模型误解了某个需求，写了处理错误的代码，又写了确认这个错误行为的测试。测试验证的是 AI 对"你想要什么"的解读，不是你真正想要的东西。

单元测试回答的是"这个函数是否返回预期输出"；它回答不了"这个应用是否做到了用户故事说的那件事"。BDD 的规格打破了闭环，因为真相来源是人工书写的验收标准，而不是 AI 的假设。

BDD 与 ATDD：一个容易被忽略的差异

维度BDDATDD
语言纯度允许少量 UI / 流程描述严格纯领域语言，禁止任何实现暗示
可执行性需要额外自动化天然可执行
协作性极强（业务 + 开发 + 测试）较强（聚焦验收定义）
对 AI 的约束强度中等极强（防止实现细节泄露进规格）

ATDD 版本完全禁止出现"注册页面""点击按钮"这类实现暗示，每条语句以句号结尾便于解析，且可直接转化为失败的验收测试。对 agent 而言，越纯的领域语言越难被它"合理地误解"。

写法：声明式优于命令式

# 差（命令式，把测试耦合到会频繁变化的实现细节）
When I click the "Login" button
And I type "alice" in the username field
And I type "secret123" in the password field
And I click "Submit"
Then I see the text "Welcome, Alice"

# 好（声明式，描述结果而非交互）
When Alice logs in with valid credentials
Then she has access to her dashboard

规范的其他要求：一个场景一个行为、用领域语言而非术语、覆盖失败路径——因为正常路径是 AI 本来就会做对的部分，边界和错误路径才是它必然遗漏的部分。

1.4 SDD：不是新发明，是旧谱系的现代实现

SDD 的概念谱系可以往上追很久：Bertrand Meyer 的 Design by Contract（1988/1992）、模型驱动工程（MDE）、形式化方法。2025 年的变化是：LLM 替换掉了那个曾经让这些方法全部失败的生成器。

现代 SDD 的两个爆发点：GitHub 在 2025 年开源的 Spec Kit（MIT，迅速积累到 7–14 万 star 量级，成为"不要工具锁定但要有方法论"的参考实现），以及 AWS 的 Kiro（IDE 原生，把规格工作流内嵌进开发环境）。

三层成熟度：这是整个领域最有用的一个框架

Thoughtworks 杰出工程师 Birgitta Böckeler 在 martinfowler.com 上的分析，区分了三个递进层级，已经成为讨论 SDD 的通用语汇：

层级做法规格生命周期代表工具门槛
L1 Spec-first先写规格再实现功能完成后规格可丢弃，下个变更写新规格Spec Kit、Kiro、BMAD低
L2 Spec-anchored规格长期保留，与代码共同演进规格进仓库，与代码一起版本管理；变更先改规格OpenSpec（明确以此为目标）中
L3 Spec-as-source人只编辑规格，代码完全生成规格是唯一真相来源，代码可随时丢弃重建Tessl（实验性）高

Böckeler 对 L3 的判断值得完整保留：它类比二十年前的模型驱动开发（用 UML/DSL 写模型、用定制生成器产代码），当年在业务应用上从未成功——抽象层级别扭、约束太严。现在 LLM 取代了生成器，约束的刚性消失了，但引入了非确定性：同一个规格跑两次，你会得到两个不同的实现。这意味着规格无法像源代码那样充当可靠的真相来源。

实践建议

大多数团队应该落在 L2。它接受少量双份维护成本，换取贴近棕地现实——你不需要把每个规格字段都做成机器可执行，只需要精确到足以驱动再生成。L1 的问题是六个月后没人知道代码为什么长这样；L3 的问题是团队在一个季度内崩回 L1，因为实现"能跑"之后就没人维护规格了。

现代 SDD 工具的标准工作流

各家命令名不同，形状是一样的：在让 agent 改动代码库之前先降低歧义。

Explore理解问题空间、既有系统、隐性依赖
Specify定义做什么和为什么，不谈技术栈
Plan技术选型、架构、数据模型
Tasks拆成有依赖顺序的原子任务
Implement对照规格与计划执行
Verify对照规格与计划验证

以 GitHub Spec Kit 为例，命令与阶段对应关系如下（它甚至官方支持 --ai codebuddy，会把整套 /speckit.* 命令写进你的 agent 命令目录）：

命令作用阶段
/speckit.constitution建立项目治理原则与开发规范地基（每项目一次）
/speckit.specify定义要构建什么（需求 + 用户故事），只讲 what/why需求（每个功能一次）
/speckit.clarify结构化提问，澄清模糊点需求校验
/speckit.checklist生成质量检查清单，被称作"英文的单元测试"需求校验
/speckit.plan选定技术栈、产出技术实现计划设计
/speckit.tasks把计划拆成可执行任务清单（含依赖顺序）拆解

AWS Kiro 的产物结构更紧凑：requirements.md（EARS 记法）、design.md（架构、时序图、数据模型、测试策略）、tasks.md（带依赖与实时状态的清单）。它提供两条起点路线：Requirements-First（绿地、产品主导、架构可以适配需求）与 Design-First（已有架构约束、严格非功能要求、需要先验证技术可行性）。

EARS：让需求可被机器解析的语法

EARS（Easy Approach to Requirements Syntax）由 Rolls-Royce 的 Alistair Mavin 等人在分析航空发动机控制系统的适航法规时提出，2009 年发表于 IEEE RE'09，被 Airbus、Bosch、Dyson、Honeywell、Intel、NASA、Siemens 等采用。2025 年起，EARS 被整合进 AI 辅助的规格驱动工具链，最显著的是 Kiro。

它的核心是承认一个事实：需求天然是模糊的，关键缺陷来自非结构化散文——复合句、"适当的""按需的"这类模糊限定词、缺失的触发条件。EARS 用固定子句顺序和极小的关键词表来约束，落在五种模板：

类型模板示例
Ubiquitous（普遍）THE <系统> SHALL <响应>移动电话 SHALL 质量小于 150 克
Event-driven（事件驱动）WHEN <触发> THE <系统> SHALL <响应>WHEN 选择静音，笔记本 SHALL 抑制所有音频输出
State-driven（状态驱动）WHILE <状态> THE <系统> SHALL <响应>WHILE ATM 中无卡，ATM SHALL 显示"请插卡开始"
Optional feature（可选特性）WHERE <包含该特性> THE <系统> SHALL <响应>WHERE 车辆有天窗，车辆 SHALL 在驾驶门有控制面板
Unwanted behaviour（非期望行为）IF <条件> THEN THE <系统> SHALL <响应>IF 输入无效信用卡号，THEN 网站 SHALL 显示"请重新输入"

规则：零到多个前置条件、零到一个触发、恰好一个系统名、一到多个系统响应。子句永远按同一时间顺序排列。研究表明，采用 EARS 的团队在设计评审阶段的需求返工通常减少 30%–50%。

Spec Kit 的宪法文件：把"必须遵守"写进每一轮生成

constitution.md 只写一次，然后被每个阶段引用。它是"跨所有 agent 交互持续存在的常驻指令"。典型内容是测试方法论要求、架构约定、代码风格、技术栈选择——本质上是给组织建立"有观点的技术栈"。一个具体例子：把从 CWE/MITRE 漏洞目录派生的安全约束编码进版本化的宪法文档，在银行微服务案例中报告安全缺陷相比无约束的 AI 生成减少 73%，同时保持开发速度。

2具体流程：产物、门禁与角色

2.1 SDD 的六阶段流程

起草提案（AI 起草，人提想法）

输入：一句想法。产出：proposal.md（为什么改）、specs/（规范增量）、tasks.md（可勾选清单）。

审查对齐（人负责决策）

人与 AI 共同审查，迭代修改直到达成共识，然后锁定规范。HITL 门禁

此时一行代码都没写，但人和 AI 对"要做什么"已经 100% 一致。这是 SDD 最反直觉、也最有价值的一步。

AI 实施（AI 负责执行）

严格按 tasks.md 执行，每完成一项勾选一项。不擅自增加已明确删除的功能。

归档更新

把规范增量合并回主 specs/ 目录，提案移入 archive/，更新版本记录。规范成为新的真相来源——也是团队的知识资产，因为它和代码是同步的。

三个必须内化的概念

① 规范即真相来源。所有关于"系统应该做什么"的知识都存储在版本可控的规范文件里。代码可以重构，规范是锚点。
② 变更即提案。任何修改都不是直接在代码上"改一改"，而是创建一个完整的变更提案文件夹（proposal + tasks + specs 增量）。提案通过审查才能进入实施。
③ AI 即履约方。AI 知道三件事——必须做什么（tasks.md）、不能做什么（规范没写的就不改）、怎样算完成（验收标准）。

2.2 BDD 的三阶段流程

Discovery：可能做什么

Three Amigos 结构化对话（业务代表 / 开发者 / 测试者），用 Example Mapping 探索具体例子。四色卡片：黄=规则、蓝=例子、红=待澄清问题、绿=验收标准。

三个角色带来的独特视角：业务方知道业务规则与优先级；开发者知道技术含义与可行性；测试者几乎本能地发现障碍和遗漏——他们会在边界情况造成问题之前就把它们识别出来。

Formulation：应该做什么

把例子写成 Gherkin 场景（Given-When-Then），精确到可自动化，并建立三方的统一语言。

Automation：实际做了什么

为每个步骤实现 step definition，把场景接到真实系统上。它们此时应该是红的（行为尚未实现），然后驱动编码。

BDD 的外环 + TDD 的内环：写 BDD 场景（功能级 RED）→ 用 TDD 实现所需组件（多个单元级 RED-GREEN-REFACTOR 循环）→ 再跑 BDD 场景（功能级 GREEN）。

2.3 Vibe Coding 的循环与边界

Prompt用自然语言表达想要什么，不写代码
GenerateAI 产出脚手架与实现，人可能完全不读
Iterate用对话式追问细化，看运行结果而非读代码
Discard关键动作：产出必须可丢弃

让它安全的唯一有效方式，是把它严格限制在可丢弃的范围内：短循环、临时分支、UI 试验、"这个库能不能做 X"。当形状稳定下来，把学到的东西提炼成一份短规格（接口、错误情形、可观测性、部署步骤），然后切换模式。

2.4 各模式的角色分工

角色在协作体系里负责什么绝对不能下放给 AI 的
业务 / 产品场景与非目标的确认与签字；优先级场景和非目标的最终确认（不必亲自写 OpenAPI）
技术负责人不变式、模块边界、公开接口约束、宪法内容架构决策的理由与边界划定
开发者写失败的测试；拥有 spec 变更权；保证 spec 与代码收敛契约的所有权——agent 可以起草契约，但永远不是契约的作者
测试 / QA边界、错误路径、验收标准完整性；视觉回归验收标准的完整性与"什么算通过"的定义
Agent起草提案、生成实现、生成 step definitions、跑测试迭代、变异测试修改 spec、定义"done"、跳过一个已锁定的门禁
多智能体编排的唯一前提

planner 和 implementer 必须共享同一份已签字的文件，而不是对同一张 ticket 的两份转述。否则你得到的是三个 agent 对一个模糊句子的三种理解。同样地，一旦某个 agent 重写了 spec.md，契约就失效了。规格变更必须由人或指定的规划 agent 持有独占权。

3协作模式：四种模式如何拼接

真正可运转的方案不是选一个，而是让它们各就其位：Vibe 负责发现、BDD 负责对齐、SDD 负责约束、TDD 负责验证。

3.1 黄金路径

探索（Vibe Coding）——限时、可丢弃

用最粗糙的方式把问题空间摸清楚：这个 API 形状合理吗？这个 UI 流程说得通吗？产物：认知，不是代码。

硬约束：会话必须短，产出在成为生产真相之前丢弃或重写。

规格化（SDD）——把认知固化成契约

写 constitution（3–5 条非可协商原则）→ 六要素 spec（结果、范围、约束、既有决策、任务、验证标准）→ plan → tasks。

硬约束：spec 阶段不谈技术栈，混入实现细节会产出过度约束的规格。HITL：规格签字

行为化（BDD）——把契约转成可执行验收

Three Amigos 提炼具体例子 → 写成声明式 Gherkin / ATDD 纯领域语言 → 这一步之后 spec 才真正"可被 agent 验证"。

硬约束：必须覆盖失败路径。HITL：场景签字

实现（TDD，外环包内环）——agent 执行，人守红

从验收测试得到目标 → 逐个单元写失败测试 → agent 生成实现 → 重构。

硬约束：写测试的 agent 与写实现的 agent 不共享上下文；先提交测试再提交实现。

验证（多层门禁）

验收测试（WHAT）+ 单元测试（HOW）双流必须同时通过；有条件时加变异测试作为第三层验证——它专门捕捉"断言被弱化到流水线能通过"的假绿。

归档（Spec-anchored）

行为变更时，spec 与代码在同一个 commit / PR 里更新。合并 spec delta 回主规格，提案归档。

违反这一条的代价："如果 spec 不在 diff 里，评审者可以合理地假设行为没有变化——而这是错的。"

3.2 三种团队形态

形态 A：单人 + 智能体

仪式更短，但不是零。

  • 动手前：20 分钟写一份文件——目标、3 个场景、2 个非目标、一条验证命令
  • 文件放在分支上，随代码走
  • 补丁之后：逐条走验收标准，标记哪些没检查
  • 个人 AGENTS.md 半屏就够，只要包含"不要发明验收标准"这条
形态 B：小队（2–8 人）

spec 进 Git，PR 承载契约评审。

  • 先约定"本次变更的契约是哪个文件"
  • PR 里把 spec 放在代码 diff 上方：评审者先接受或拒绝意图，再看实现
  • Definition of Ready 参与门禁
  • 这能削减验证债务——跨一千行争论"为什么"已经太晚
形态 C：多智能体编排

协调成本换并发能力，只在稳定后扩展。

  • 任务级规格支持安全的并发：协调 agent 派发多个实现 agent 到独立任务，验证 agent 检查每个产出
  • 规格被描述为"超级 prompt"，把工作按上下文窗口切成模块
  • 顺序：先稳定单 agent → 再加第二个（验证）agent 度量返工率 → 最后才扩到 swarm
  • 从 2 个 agent 跳到 4 个，是大多数团队引入协调 bug 的地方
贯穿：探索态

对任何形态都保留一条低成本的探路通道。

  • 探索性工作继续 vibe coding——它是发现"问题是什么"的正确工具
  • 唯一要求：把手交接口显式化
  • 当 spike 教会你这件事的形状，停下来，提炼规格，按规格重建生产版本

3.3 为什么是现在是这个组合

三个来自方法论之父与顶级工程组织的判断，指向同一件事：

  • Kent Beck（TDD 创造者）：被淘汰的技能是语法和语言专精；被放大的技能是愿景、策略、任务拆解和判断力。他同时明确说 TDD 在 AI 时代是超能力，因为 agent 会不断引入回归，而测试是唯一可靠的护栏。
  • Dave Farley：验证是新的瓶颈。"我没法足够仔细地读 12,000 行代码。信任必须来自可执行规格和持续验证。"
  • Martin Fowler 团队（2026 年 retreat）：写代码从来不是瓶颈。这意味着 AI 的速度倍增在缺乏工程实践时会变成债务倍增。

贯穿案例：给一个已有的博客系统增加"深色模式"。选它是因为棕地改造最真实——绿地项目可以随便重来，棕地不行。

步骤 3：Spec 的六要素结构

# 深色模式 · 规范增量

## 1. 结果（Outcomes）
夜间阅读场景下，用户可将界面切换为深色主题。

## 2. 范围（Scope）
- 设置页主题开关（浅色 / 深色）
- 主题状态持久化
- 文章阅读页样式适配

## 3. 非目标（Non-goals）   ← 没有非目标清单就不算准备好
- 不实现"跟随系统"自动切换
- 不改动导航栏配色
- 不为第三方嵌入内容（评论区）提供深色样式

## 4. 约束（Constraints）
- 主题状态 MUST 存于 localStorage，键名 `theme`
- 深色样式 MUST 通过 CSS 变量实现，禁止覆盖白模式样式表
- 图片与代码块 MUST 在深色模式下保持原色

## 5. 验收标准（可证伪，EARS 风格）
WHEN 用户在设置页点击"深色模式"开关
THE 系统 SHALL 立即应用深色主题，且不重载页面。

IF localStorage 中不存在 `theme` 键
THEN 系统 SHALL 默认使用浅色主题。

WHEN 用户在深色模式下访问文章阅读页
THE 系统 SHALL 应用深色背景与浅色正文，同时保持图片原色。

## 6. 验证方式（Agent 用作证明的命令）
- `npm test -- theme`           单元测试
- `npm run test:e2e -- theme`   场景验收
- `npm run build`               构建无错误

constitution.md（项目宪法，只写一次）

# 项目宪法

## 不可协商的原则

1. **测试先行**：任何生产代码之前必须有失败的测试。
   缺少对应测试的生产代码变更禁止合并。

2. **行为变更同 PR**：行为发生变化时，spec 与代码必须在同一个 commit 中更新。
   spec 未出现在 diff 中，视为行为未变更。

3. **依赖审批**：新增运行时依赖需要技术负责人在 PR 中显式批准。

4. **可观测性默认值**：所有对外接口必须记录结构化日志（请求 ID、耗时、结果状态）。

5. **安全基线**：禁止将密钥写入代码或配置文件；用户输入必须经过显式校验层。

## 规格所有权
spec 只能由人或指定的规划 agent 修改。实现 agent 无权编辑 spec 文件。
若实现中发现 spec 有问题，输出建议并停止，等待人确认。

5失败模式与争议

这一节是报告里最实用的部分。SDD 的相关实践失败，绝大多数不是"模型不够聪明"，而是十几类可预测、可预防的流程问题。

5.1 十二类失败模式

#失败模式表现修复
1规范漂移
（Thoughtworks 认定的首要失败模式）		代码改了、spec 没改。三个 agent PR 之后文件还写着"折扣在服务端计算"，而逻辑已经"为了更快"挪到客户端。下一个 agent 读到契约，把正确的决策当 bug 改回去。行为变化时 spec 与代码同 commit；spec 不在 diff 里则评审者可假设行为未变——而这是错的
2过度规格化spec 写得像伪代码，agent 失去自由度，任何偏离都被当作 bug。Anthropic 的 harness 论文指出：单个功能的 spec 超过约 800 行后，agent 在新颖任务上的吞吐急剧下降。匹配规格重量与工作重量。一行修复的 spec 就是 commit message 里的一句话。
3不可证伪的需求"系统要快"而非"p95 延迟在 1000 RPS 下低于 200ms"。agent 会以满足字面文本、别的什么都不满足的方式实现它。写完每条标准问自己："我现在能写出一条确定性测试吗？"不能就重写。
4让 agent 编辑 spec一旦某个 agent 重写 spec.md 让测试通过，契约就没了。这通常表现为"测试莫名其妙全绿了"。spec 变更权独占。工具层和提示词层双重禁止，CI 检测 spec 文件是否被实现 agent 修改。
5假绿测试AI 先写完代码，再被要求"补覆盖率"。它编码的是事实而不是意图；更糟的是它会弱化断言让流水线通过。绿色意味着测试同意了补丁，而不是同意了契约。验收标准先于代码存在；测试可追溯到 spec 条目；评审者可以问"这条测试检查的是契约的哪一条"——答不上来就是装饰。
6把 SDD 当瀑布spec 写一次、冻结、交给下游实施六个月。循环从分钟级退化到周级。spec 是主权者，但它也是活的。如果 spec 在第一次 agent 运行后不能改，你就重新发明了行业花了三十年才逃出来的瀑布。
7规范过于宽泛"优化一下结账"、"清理一下授权"、"改得像现代 SaaS"。对人这是一句对话开场白，对 agent 这是一张重写整个模块的许可证。宽泛的 spec 产出宽泛的补丁、宽泛的评审，以及没人主动选择的架构漂移。一个 spec 一个行为变更；非目标写成清单；限制目录与公开接口范围。
8双重真相来源wiki、README、spec.md 三者互相矛盾，agent 挑最方便的那个。spec 必须在仓库里、版本可控、与行为同一 commit 变更。放在 wiki、共享盘或项目管理工具里的 spec 会在一两个 sprint 内失同步。
9腐烂的宪法规则没人执行，于是模型学会了忽略它。这是最隐蔽的一种——它教坏了 agent。宪法要短（3–5 条），且每条都有对应的自动检查或明确的评审动作。
10评审错的产物在格式和风格上留评论，而验收标准本身是错的。把 spec 放在代码 diff 上方。先接受或拒绝意图，再看实现。
11没人签字的 agent 草稿由 agent 起草、没有人读过的 spec 充当真相来源。模型起草契约是有用的；但一份没人读过的真相来源，等于多了一个文件的 vibe coding。意图的签字权留给为事故买单的人。
12审查过载重型框架每个阶段都生成大量文档，开发者审查规范文件花的时间和精力远超直接审代码。SDD 本想减少返工、提升效率，结果变成了额外负担。spec 必须能一口气读完。用判断标准："评审这份 spec 是否比直接实现它更便宜？"

5.2 争议：SDD 是"越改越坏的改进"吗

SDD 在 2025–2026 年成为热点的同时，也收到了来自行业内部的严肃批评。这些批评必须被完整呈现，否则任何 SDD 的采纳都会在第一次受挫时就崩掉。

批评一：Böckeler 的 Verschlimmbesserung

Thoughtworks 的 Birgitta Böckeler 在那篇被广泛引用的分析里，用德语词 Verschlimmbesserung 形容 SDD——意思是"越改越坏的改进"。她给出的核心发现是：SDD 的层级越高，理论上收益越大，但实际应用中遇到的问题也越多。她同时点出了一个反直觉的观察：不少人认为规范越详细 AI 就越听话、执行越精准，但实测结果恰恰相反——AI 依然会忽视指令、过度执行，规范的冗长程度与 AI 的遵从程度之间没有线性关系。

批评二：它是换了名字的瀑布

一个被反复提出的论证链：SDD 本质上重现了瀑布方法——大设计前置、穷尽式规格、假设充分的规划能消除执行不确定性。有人做了实测对照：一次实践需要 33 分钟、2,577 行 markdown 才产出 689 行代码，对比迭代提示方法的 8 分钟——约慢 10 倍，且质量无提升。

更根本的反驳是规格的非确定性：SDD 把规格当作权威真相来源，但 LLM 是非确定性的——同一个规格在不同运行中产出不同实现，架构选择、数据结构、错误处理都会变。这意味着规格无法像源代码那样充当可靠的真相来源。

批评三：模型驱动开发的重复

Böckeler 自己就指出 L3 与二十年前的 MDE 的相似性。当年人们用 UML 或 DSL 写模型、用定制生成器产代码，它从未在业务应用上普及。现在 LLM 替换了生成器：抽象层级别扭的问题解决了，但代价是非确定性。历史是否重演尚待观察。

我的判断

SDD 的价值不在于"文档"，而在于三件事：把决策前置到它还很便宜的时候、让变更可追溯、给 agent 一个它自己无法定义的退出条件。前两条是老生常谈，第三条是 AI 时代新增的、也是唯一不可替代的。

它在实践中失败的原因几乎总是同一个：人不维护 spec。这不是方法论的缺陷，是纪律的缺陷——而讽刺的是，SDD 的批评者与拥护者在这里其实是一致的：都承认"一份没人维护的 spec 比没有 spec 更糟，因为它主动误导"。

最务实的结论来自实践者：工具选择远不如产物质量重要。一份含糊的 Kiro 验收标准和一份含糊的 prompt 一样会漂移；一份五十任务的 Spec Kit 计划在任何 agent 下都像瀑布。真正可移植的实践是这几条——spec 能一口气读完、显式写出非目标、每个任务的 diff 人类可读、合并前对照验收标准验证、实现过程中发现更好的路径时回头更新 spec。

最后一句话

AI 编码 agent 不会变得更弱，它们会变得更快、更自主。这意味着把它们指向错误目标的代价在持续上升。

在 2026 年做对这件事的团队，不是那些 prompt 写得最巧的团队，而是那些在 agent 跑起来之前就已经决定好"done"是什么意思的团队。方法是：写 spec，让它成为主权者，让它保持活着。
